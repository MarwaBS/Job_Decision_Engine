# Job Decision Engine — FULL transitive dependency lock.
#
# requirements.txt pins the DIRECT dependencies exactly (==). This file
# locks the entire transitive universe (every wheel that ends up in the
# shipped image), so a transitive release can never silently change — or
# re-introduce a vulnerability into — what was tested.
#
# Why this exists (2026-07 re-audit, ROUND 6 item B3): the deployed set
# once carried starlette 1.2.1 (PYSEC-2026-248 / PYSEC-2026-249, fixed in
# 1.3.0 / 1.3.1) because transitives were resolved at image-build time,
# not locked. This lock pins starlette 1.3.1 and torch 2.12.1 (outside
# the CVE-2025-3000 affected range — 2.12.0 was inside it). CI runs
# `pip-audit` against this file on every push so a new advisory turns the
# build red instead of rotting silently.
#
# Consumed as a pip CONSTRAINTS file everywhere installs happen:
#   pip install -r requirements.txt -c requirements-lock.txt
# (Dockerfile + both CI install steps — the shipped image and the tested
# universe are the same set.)
#
# How to regenerate (universal, cross-platform markers, Python 3.12 —
# the version in the Dockerfile base image and CI):
#   uv pip compile requirements.txt --universal --python-version 3.12 \
#       --no-header --annotation-style=line -o requirements-lock.txt
# then reapply this header, re-run the full test suite in a FRESH venv
# installed with the new lock, and let CI's pip-audit gate pass.
